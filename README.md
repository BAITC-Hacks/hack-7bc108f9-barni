Платформа помогает бизнесу превратить слабое описание задачи в структурированную и готовую к работе карточку. AI анализирует исходное описание, находит недостающую информацию и задаёт уточняющие вопросы. После подтверждения данных система рассчитывает прозрачный рейтинг готовности задачи от 0 до 100.

Опубликованные задачи попадают в общий каталог. Студенческие команды самостоятельно выбирают интересующие задачи и отправляют предложения, а бизнес вручную принимает или отклоняет их.

## Основной сценарий

```text
Слабое описание бизнеса
        ↓
AI-анализ
        ↓
Недостающие сведения + уточняющие вопросы
        ↓
Ответы бизнеса
        ↓
AI формирует карточку
        ↓
Ручное редактирование и подтверждение
        ↓
Рейтинг готовности 0–100
        ↓
Публикация в каталоге
        ↓
Студенческая команда выбирает задачу
        ↓
Отправляет предложение
        ↓
Бизнес вручную принимает / отклоняет
```

AI не выбирает команду и не принимает решения за пользователя.

Ответственность разделена следующим образом:

- **AI** извлекает предоставленные сведения, определяет пробелы, формирует уточняющие вопросы и структурирует карточку.
- **Backend** валидирует данные, рассчитывает рейтинг, хранит задачи и предложения, публикует и сортирует задачи.
- **Человек** редактирует и подтверждает сведения и самостоятельно принимает или отклоняет предложения команд.

# AI-функциональность

AI используется для двух содержательных операций:

1. анализа первоначального описания задачи;
2. формирования структурированной карточки после уточнений.

AI **не рассчитывает рейтинг**, не публикует задачу и не выбирает команду.

## 1. Анализ черновика

```http
POST /api/ai/analyze-draft
```

Пример:

```json
{
  "draft": "Хотим улучшить обработку заявок клиентов",
  "topic": "Автоматизация"
}
```

AI извлекает только известные сведения, определяет пробелы и формирует минимум три уточняющих вопроса.

Пример результата:

```json
{
  "known_fields": {
    "need": "Хотим улучшить обработку заявок клиентов"
  },
  "missing_fields": [
    "context",
    "users",
    "data",
    "constraints",
    "expected_result",
    "success_criteria",
    "contact",
    "interaction_format"
  ],
  "questions": [
    {
      "id": "q1",
      "target_field": "context",
      "text": "Как сейчас обрабатываются заявки?"
    },
    {
      "id": "q2",
      "target_field": "data",
      "text": "Какие данные по заявкам доступны?"
    },
    {
      "id": "q3",
      "target_field": "success_criteria",
      "text": "Какой измеримый результат будет считаться успешным?"
    }
  ]
}
```

## 2. Формирование карточки

```http
POST /api/ai/build-card
```

AI получает исходное описание и ответы пользователя и формирует структурированную карточку.

Пример:

```json
{
  "card": {
    "title": null,
    "topic": "Автоматизация",
    "context": "Заявки приходят в WhatsApp и обрабатываются вручную",
    "need": "Хотим улучшить обработку заявок клиентов",
    "users": null,
    "data": null,
    "constraints": null,
    "expected_result": null,
    "success_criteria": null,
    "contact": null,
    "interaction_format": null
  }
}
```

Все поля карточки доступны пользователю для ручного редактирования перед подтверждением.

# Grounding и ограничения AI

Ключевой принцип AI-модуля:

> AI использует только информацию, явно предоставленную пользователем.

Модель не должна самостоятельно придумывать:

- данные и датасеты;
- пользователей;
- сроки;
- технологии;
- ограничения;
- контакты;
- числовые показатели;
- ожидаемые результаты;
- критерии успеха.

Если сведений недостаточно, значение остаётся:

```json
null
```

Для MVP используется консервативная grounding-проверка: извлечённые моделью значения проверяются относительно исходного `draft` и ответов пользователя.

AI может структурировать предоставленные сведения, но не должен добавлять новые бизнес-факты.

Перед публикацией карточка в любом случае редактируется и подтверждается человеком.

---

# Structured Outputs

AI-модуль использует официальный OpenAI Python SDK и Structured Outputs.

Вызов выполняется через:

```python
AsyncOpenAI.responses.parse(...)
```

с Pydantic-схемами.

Сырой ответ модели не передаётся frontend.

Порядок обработки:

```text
OpenAI
  ↓
Structured Output
  ↓
Pydantic validation
  ↓
Grounding validation
  ↓
API response
```

На AI-запрос установлен timeout 20 секунд.

При невалидном structured output выполняется максимум один повторный запрос.

# AI fallback

Для анализа черновика реализован локальный fallback.

Если OpenAI API недоступен, система может вернуть шаблонные вопросы по недостающим полям.

Например:

- Как сейчас устроен процесс, который вы хотите изменить?
- Какие данные или материалы вы сможете предоставить команде?
- Какой конкретный результат должна подготовить команда?
- По каким измеримым признакам вы поймёте, что результат успешен?
- Есть ли ограничения по срокам, технологиям или доступам?

Fallback не пытается придумывать бизнес-факты.

Режим можно определить по HTTP header:

```text
X-AI-Fallback: true
```

Реальная модель:

```text
X-AI-Fallback: false
```

Fallback является режимом деградации и не считается успешным live-тестом AI.

# Рейтинг готовности

Рейтинг отражает **готовность конкретной задачи к работе со студентами**, а не известность компании.

AI рейтинг не рассчитывает.

Расчёт выполняется детерминированной функцией backend.

| Поле | Баллы |
|---|---:|
| Контекст | 10 |
| Потребность | 10 |
| Данные и материалы | 20 |
| Ожидаемый результат | 15 |
| Критерии успеха | 15 |
| Ограничения | 10 |
| Пользователи | 10 |
| Контакт | 5 |
| Формат взаимодействия | 5 |
| **Всего** | **100** |

Баллы начисляются за заполненные и подтверждённые сведения.

Длинный текст сам по себе дополнительных баллов не даёт.

---

## Уровни готовности

| Баллы | Уровень |
|---:|---|
| 0–39 | Черновик |
| 40–69 | Рабочая |
| 70–89 | Готовая |
| 90–100 | Приоритетная |

Низкий рейтинг:

- не скрывает задачу;
- не запрещает публикацию;
- не запрещает студенческим командам отправлять предложения.

После изменения и подтверждения карточки рейтинг пересчитывается.

Изменение рейтинга влияет на позицию задачи в каталоге.

# Каталог

Все опубликованные задачи доступны студенческим командам.

Поддерживаются:

- сортировка по рейтингу;
- фильтрация по теме;
- фильтрация по уровню готовности;
- просмотр полной карточки;
- просмотр рейтинга;
- просмотр недостающих сведений.

По умолчанию задачи могут отображаться по убыванию рейтинга.

При увеличении рейтинга задача меняет позицию в каталоге.

# Предложения студенческих команд

Команда самостоятельно выбирает задачу.

Предложение содержит:

```text
Идея решения
План реализации
Предполагаемый срок
Ссылка на прототип
```

Новое предложение получает статус:

```text
pending
```

Бизнес вручную выполняет одно из действий:

```text
accepted
rejected
```

Автоматического назначения команды нет.

Для одной задачи может существовать несколько предложений, и бизнес может принять одну, несколько или ни одной команды.

Тесты не требуют API-ключа, сети или платных вызовов:

Live-тесты запускаются отдельно и используют API-квоту:

```powershell
$env:RUN_LIVE_AI = '1'

.\.venv312\Scripts\python -m pytest -c backend/pytest.ini backend/tests/test_ai_live.py -q -p no:cacheprovider

```

Без:


```text
X-AI-Fallback: false
```

Поэтому шаблонный fallback не может случайно выдать себя за успешную проверку модели.

# Обработка ошибок

AI-модуль предусматривает контролируемую деградацию.

При ошибке:

- исходный `draft` не теряется;
- ответы пользователя не теряются;
- frontend может повторить запрос;
- сырые ответы OpenAI не возвращаются клиенту;
- секреты не записываются в лог;
- пользовательские тексты не записываются в provider-error logs.

Основные AI errors:

```typescript
type AIError = {
  detail: {
    code:
      | "ai_unavailable"
      | "ai_invalid_output"
      | "insufficient_missing_fields";
    message: string;
    retryable: boolean;
  };
};
```

При ошибках валидации FastAPI используется стандартный HTTP `422`.

# Демонстрационный сценарий

Полный сценарий выполняется внутри приложения:

```text
1. Бизнес вводит слабое описание задачи.

2. AI возвращает минимум 3 уточняющих вопроса.

3. Бизнес отвечает.

4. AI формирует структурированную карточку.

5. Бизнес вручную редактирует одно из полей.

6. Бизнес подтверждает карточку.

7. Backend рассчитывает рейтинг.

8. Показывается рост рейтинга и breakdown.

9. Задача публикуется.

10. Задача появляется в каталоге согласно рейтингу.

11. Роль переключается на студенческую команду.

12. Команда открывает задачу.

13. Команда отправляет предложение.

14. Роль переключается обратно на бизнес.

15. Бизнес вручную принимает или отклоняет предложение.
```

# Известные ограничения

Это hackathon MVP, поэтому намеренно не реализованы:

- полноценная регистрация;
- восстановление пароля;
- сложный RBAC;
- realtime chat;
- уведомления;
- календарь;
- файловое хранилище;
- RAG;
- vector database;
- обучение собственной модели;
- multi-agent framework;
- полноценная LMS;
- мобильное приложение;
- production infrastructure;
- полный project tracker.

AI grounding является консервативной защитой MVP, а не формальным доказательством фактической корректности.

Проверка типов также не гарантирует семантическую правильность ответа модели.

Поэтому окончательная карточка всегда остаётся под контролем человека и требует ручного подтверждения.

# Использование Codex

Codex использовался как обязательный инструмент разработки.

Работа разбивалась на небольшие изолированные задачи вместо генерации всей платформы одним запросом.

В частности, Codex использовался для:

- реализации AI schemas;
- интеграции Structured Outputs;
- AI validation;
- grounding-проверок;
- fallback-механизма;
- unit-тестов;
- live AI-тестов;
- проверки edge cases;
- анализа ошибок интеграции;
- улучшения системного prompt после обнаружения смешения `need` и `context`;
- проверки качества и структуры кода.

После генерации изменения проверялись разработчиками и автоматическими тестами.

# Definition of Done

MVP считается готовым, если после:

```bash
docker compose up --build
```

без изменения исходного кода можно выполнить:

```text
✓ открыть frontend
✓ создать черновик
✓ получить AI-вопросы
✓ ответить на вопросы
✓ получить карточку
✓ отредактировать карточку
✓ подтвердить сведения
✓ получить рейтинг 0–100
✓ опубликовать задачу
✓ увидеть её в каталоге
✓ отправить предложение от студенческой команды
✓ принять или отклонить предложение от лица бизнеса
✓ сохранить данные после перезапуска
```

Главный принцип проекта:

> AI помогает бизнесу сформулировать качественную задачу.  
> Прозрачный рейтинг мотивирует её улучшить.  
> Студенты самостоятельно выбирают задачи.  
> Финальное решение всегда остаётся за человеком.
