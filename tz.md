Техническое задание v1
Платформа рейтинга бизнес-задач и открытого выбора студенческих команд
1. Цель продукта
Создать работающий MVP, в котором:
Бизнес вводит слабое описание задачи
→ AI находит пробелы и задаёт минимум 3 вопроса
→ формируется редактируемая карточка
→ бизнес подтверждает сведения
→ система рассчитывает прозрачный рейтинг 0–100
→ задача публикуется в общем каталоге
→ студенческая команда отправляет предложение
→ бизнес вручную принимает или отклоняет предложение
Главный результат кейса — полный сквозной сценарий от черновика до публикации, отклика и ручного выбора команды. Основная геймификация направлена на бизнес: более полная задача получает более высокий рейтинг и позицию в каталоге.

2. Обязательное решение
2.1. Пользователи
Представитель бизнеса
Может:
    • создать черновик задачи;
    • ответить на AI-вопросы;
    • отредактировать карточку;
    • подтвердить сведения;
    • увидеть рейтинг и причины начисления;
    • опубликовать задачу;
    • просмотреть предложения команд;
    • вручную принять или отклонить каждое предложение.
Студенческая команда
Может:
    • открыть общий каталог;
    • сортировать и фильтровать задачи;
    • открыть подробную карточку;
    • отправить предложение;
    • увидеть статус собственного предложения.
Упрощение для MVP
Полноценную регистрацию не делать. В шапке приложения использовать демонстрационный переключатель:
Режим:
[Бизнес] [Студенческая команда]
Для команды использовать выбор одного из заранее созданных профилей.

3. Сквозной пользовательский сценарий
Сценарий бизнеса
    1. Бизнес вводит:
Хотим улучшить обработку заявок клиентов.
    2. Нажимает Проанализировать.
    3. AI возвращает:
    • найденные сведения;
    • недостающие поля;
    • минимум 3 уместных вопроса.
Пример:
1. Где сейчас поступают заявки?
2. Какие данные по заявкам доступны?
3. Какой результат будет считаться успешным?
4. Есть ли ограничения по срокам и технологиям?
    4. Бизнес отвечает.
    5. AI формирует карточку.
    6. Бизнес редактирует карточку вручную.
    7. Нажимает Подтвердить и пересчитать.
    8. Backend рассчитывает рейтинг.
    9. Бизнес видит:
Рейтинг: 75/100
Уровень: Готовая

Начислено:

Ограничения: 10/10

Не хватает:

Формат обратной связи: 0/5
    10. Бизнес публикует задачу.
    11. Задача появляется в каталоге на позиции по рейтингу.
Сценарий студента
    1. Команда открывает каталог.
    2. Фильтрует задачи.
    3. Открывает задачу.
    4. Отправляет:
Идея решения
План реализации
Предполагаемый срок
Ссылка на прототип
    5. Предложение сохраняется со статусом pending.
Решение бизнеса
Бизнес открывает предложения и выполняет ручное действие:
[Принять] [Отклонить]
Можно принять одну, несколько или ни одной команды. Автоматический выбор запрещён.

5. Карточка бизнес-задачи
Обязательные поля
{
  "title": "Название задачи",
  "topic": "Тема",
  "context": "Что происходит сейчас",
  "need": "Что требуется изменить",
  "users": "Для кого создаётся решение",
  "data": "Какие данные и материалы доступны",
  "constraints": "Сроки, технологии, доступы и ограничения",
  "expected_result": "Какой результат должен получить бизнес",
  "success_criteria": "Как измеряется успешность",
  "contact": "Контакт представителя бизнеса",
  "interaction_format": "Формат консультаций и обратной связи"
}
AI не должен заполнять поля предположениями. Неизвестные значения:
{
  "data": null,
  "success_criteria": null
}
Пользователь должен иметь возможность изменить каждое поле до подтверждения.

6. Рейтинг задачи
6.1. Принцип
Рейтинг отражает готовность конкретной задачи к работе, а не известность компании. Баллы начисляются за заполненные и подтверждённые сведения. Низкий рейтинг не скрывает задачу из каталога.
6.2. Формула
Использовать рекомендованные веса из кейса.
Поле
Баллы
Контекст
10
Потребность
10
Данные и материалы
20
Ожидаемый результат
15
Критерии успеха
15
Ограничения
10
Пользователи
10
Контакт
5
Формат взаимодействия
5
Всего
100
Комбинированные критерии кейса разделены на отдельные поля, но их общий вес сохранён.
6.3. Реализация
Рейтинг рассчитывается обычной Python-функцией, не моделью:
def calculate_score(card: TaskCard) -> ScoreResult:
    ...
Возвращаемая структура:
{
  "score": 75,
  "readiness_level": "ready",
  "breakdown": [
    {
      "field": "context",
      "label": "Контекст",
      "earned": 10,
      "maximum": 10,
      "reason": "Контекст указан"
    }
  ],
  "missing_fields": [
    {
      "field": "success_criteria",
      "label": "Критерии успеха",
      "potential_points": 15,
      "recommendation": "Добавьте измеримые признаки успешного результата"
    }
  ]
}
6.4. Уровни готовности
0–39   — Черновик
40–69  — Рабочая
70–89  — Готовая
90–100 — Приоритетная
6.5. Правила
    • До подтверждения можно показывать Предварительный рейтинг.
    • Официальный рейтинг сохраняется после Подтвердить и пересчитать.
    • Минимального рейтинга для публикации нет.
    • Минимального рейтинга для отклика нет.
    • После пересчёта каталог должен изменить порядок задач.
    • Нельзя начислять баллы просто за длинный текст.
    • Сумма breakdown обязана совпадать с итоговым рейтингом.

7. AI-функциональность
Обязательное
В MVP должна быть минимум одна содержательная AI-функция. AI может анализировать полноту, генерировать вопросы и преобразовывать ответы в карточку. Он не должен добавлять неизвестные факты, выбирать команду или автоматически назначать исполнителей.
7.1. AI-операция №1: анализ черновика
Endpoint
POST /api/ai/analyze-draft
Вход
{
  "draft": "Хотим улучшить обработку заявок клиентов",
  "topic": "Автоматизация"
}
Выход
{
  "known_fields": {
    "need": "Улучшить обработку заявок клиентов"
  },
  "missing_fields": [
    "context",
    "users",
    "data",
    "constraints",
    "expected_result",
    "success_criteria",
    "contact",
    "interaction_format"
  ],
  "questions": [
    {
      "id": "q1",
      "target_field": "context",
      "text": "Как сейчас обрабатываются заявки?"
    },
    {
      "id": "q2",
      "target_field": "data",
      "text": "Какие данные по заявкам доступны?"
    },
    {
      "id": "q3",
      "target_field": "success_criteria",
      "text": "Какой измеримый результат будет считаться успешным?"
    }
  ]
}
Валидация
    • questions.length >= 3;
    • каждый вопрос непустой;
    • каждый вопрос относится к недостающему полю;
    • AI не возвращает придуманные факты.
7.2. AI-операция №2: создание карточки
Endpoint

Вход
{
  "draft": "Хотим улучшить обработку заявок клиентов",
  "answers": [
    {

    "title": "Оптимизация обработки клиентских заявок",
    "context": "Заявки поступают в WhatsApp и обрабатываются вручную",
    "need": "Сократить время обработки заявок",
    "users": null,
    "data": null,
    "constraints": null,
    "expected_result": null,
    "success_criteria": null,
    "contact": null,
    "interaction_format": null
  }
}
7.3. Системное правило AI
Используй только информацию, которую сообщил пользователь.
Не делай предположений о компании, данных, сроках, метриках,
технологиях, контактах или пользователях.

Если сведений недостаточно, верни null.
Сформулируй минимум 3 вопроса только по недостающим сведениям.
Ответ должен строго соответствовать заданной JSON-схеме.
7.4. Обработка ошибок
При некорректном ответе модели:
    1. проверить ответ через Pydantic;
    2. выполнить не более одного повторного запроса;
    3. при повторной ошибке вернуть понятное сообщение;
    4. не терять исходный текст и ответы;
    5. показать кнопку Повторить;
    6. иметь локальный fallback с шаблонными вопросами по пустым полям.

18. Критерии приёмки
Обязательное
AC-01. AI-вопросы
При слабом описании система возвращает минимум 3 уместных вопроса.
AC-02. Отсутствие выдумок
Если пользователь не указал данные, контакты или метрики, соответствующие поля остаются пустыми.
AC-03. Редактирование
Все поля карточки доступны для ручного изменения.
AC-04. Рейтинг
Рейтинг находится в диапазоне 0–100.
AC-05. Прозрачность
Для каждого балла видно:
    • за что он начислен;
    • сколько можно получить;
    • чего не хватает.
AC-06. Пересчёт
Добавление подтверждённого поля меняет рейтинг.
AC-07. Каталог
Опубликованная задача появляется в каталоге.
AC-08. Сортировка
Задачи располагаются по убыванию рейтинга.
AC-09. Низкий рейтинг
Задача с рейтингом ниже 40 остаётся доступна.
AC-10. Отклик
Студенческая команда может отправить предложение.
AC-11. Несколько предложений
Одна задача принимает несколько предложений.
AC-12. Ручное решение
Бизнес вручную принимает или отклоняет каждое предложение.
AC-13. Несколько победителей
Можно принять несколько предложений.
AC-14. Ошибка AI
При ошибке API пользовательский ввод не теряется.
AC-15. Перезапуск
После перезапуска контейнеров сохранённые задачи и решения остаются в PostgreSQL.

20. Демонстрация
Обязательный сценарий
1. Ввести слабое описание.
2. Получить минимум 3 вопроса.
3. Ответить на вопросы.
4. Получить карточку.
5. Отредактировать карточку.
6. Подтвердить.
7. Показать рост рейтинга.
8. Опубликовать.
9. Показать изменение позиции в каталоге.
10. Переключиться на студента.
11. Отправить предложение.
12. Переключиться на бизнес.
13. Принять или отклонить предложение.
Все переходы должны работать в приложении, а не на слайдах.
Демо до 2 минут
0:00–0:15 — проблема и слабое описание
0:15–0:35 — AI-вопросы и готовые ответы
0:35–0:55 — карточка и подтверждение
0:55–1:10 — рейтинг и публикация
1:10–1:25 — каталог и позиция
1:25–1:40 — предложение студента
1:40–2:00 — ручное решение бизнеса

24. Definition of Done
MVP считается готовым только когда одной командой выполняется без изменения кода:
docker compose up --build
После запуска:
1. Открывается frontend.
2. Создаётся черновик.
3. AI возвращает вопросы.
4. Формируется карточка.
5. Рейтинг рассчитывается.
6. Задача публикуется.
7. Задача появляется в каталоге.
8. Команда отправляет предложение.
9. Бизнес принимает или отклоняет предложение.
10. Данные сохраняются после перезапуска.
Любая дополнительная функция, которая не помогает этому сценарию, откладывается.
